# Automatic Proxmox node connector pairing

The Proxmox node pairing form now offers Connect Automatically with SSH after selecting a discovered node. It resolves the node IP from the saved Proxmox connection, asks for fresh Linux root/sudo credentials, masked SSH fingerprint verification and explicit installation consent. Manual pairing remains available. Standalone Docker automatic installation is outside this change.

Owner-only HTTPS endpoints start and poll a background installation. Target IP and connection binding are checked on submission and before remote mutation. SSH pins the approved host key. A fixed Python preflight checks the actual hostname, Proxmox tools, existing connector files and the node's HTTPS access to the controller before creating pairing credentials. Secrets and source payload are passed over SSH stdin, never shell arguments. Config/source writes refuse existing files, preserve restrictive permissions and roll back newly created files if service setup fails. Only the new connector service is enabled and started. No packages, VM/CT power actions or Docker engine restarts are performed.

The standard controller installer/updater exports Caddy's public local root certificate into the existing read-only API CA mount. It never exports Caddy private keys or mounts Caddy's private state into the API. Automatic pairing stores that public certificate in the connector's protected configuration. The connector verifies HTTPS using this certificate plus normal system trust. Other private controller CAs can be provided at the documented public-certificate path. Global node trust settings are unchanged.

Success requires a fresh heartbeat from the new pairing with the expected connector source revision. Missing heartbeat remains unverified and can complete after a later matching heartbeat. Existing registrations are protected against duplicate pairing. Failed remote installation revokes the newly created controller credential. Installation whose result is uncertain must be inspected on the node before retrying. Job tracking and fresh passwords are held in memory only; an API restart requires checking existing connections and the node service before another attempt.

Validation: real local SSH server verifies sudo password and pairing payload remain on stdin; API fixtures cover permissions, HTTPS, approvals, node binding, failure sanitization, credential revocation, duplicate starts and heartbeat verification; a root-directory Python fixture checks wrong-node refusal, no overwrite, file permissions and service-failure rollback. A public-CA export fixture checks the exact public certificate and stale-file removal. UI fixtures check selected IP, consent, password clearing and heartbeat polling. Full API/web tests and production build are checked before merging. No live customer Proxmox node, actual privileged systemd installation or physical mobile browser was used.
